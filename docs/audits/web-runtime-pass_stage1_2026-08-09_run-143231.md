## 1 · Environment bring-up (this is itself a finding)

**Infra (already present, reused):** Docker was running with all six dev containers already up ~3 days — Postgres (`:5434`, healthy), Redis, Meilisearch, MinIO, Temporal, Mailhog (`docker-compose.dev.yml`). A `.env` existed. I did not have to provision infra.

**App processes I started:** `apps/api` (`tsx watch`, `:3001`) and `apps/web` (`next dev --webpack`, `:3000`), each with `.env` loaded via `dotenv`. Both started cleanly — API printed `STARTUP READY`, web compiled `/login` and served HTTP 200.

**🚩 BLOCKER — the app would not run until I applied 14 pending migrations.** With the stack up, **login failed**: `auth.login` returned **HTTP 500 — `column "esi_establishment_number" does not exist`** (surfaced raw to the browser console). Investigation:
- The drizzle journal head is `0074_ambiguous_rick_jones` (75 migrations, 0000–0074).
- The DB's `drizzle.__drizzle_migrations` ledger showed only **61 applied** — **migrations 0061–0074 had never been run** against this local DB.
- Consequently the schema the code expects was absent: `organizations.esi_establishment_number` (mig `0074`) missing, and `audit_chain_anchors` (mig `0062`) missing entirely.
- **Fix applied:** `pnpm db:migrate` → "migrations applied successfully"; ledger advanced, both objects now exist, table count 237 → **238**. Login then succeeded (`admin@coheron.com` / `demo1234!`, owner) and I reached `/app/**`.

**Why the setup step matters (a customer could not do it, but the failure mode is the finding):** production auto-applies migrations via the `migrator` service, so a real tenant would not hit this. But the *local runtime's* failure mode is poor: the API booted and served traffic against a schema it could not query, and the only symptom was a **500 with a raw Postgres column name leaked to the client** on the login mutation — not a startup refusal, not a friendly error. A developer bringing the stack up from this DB state gets a dead login and a cryptic console error. **Static analysis (run-131837) could not have surfaced this** — it is a live DB/migration-state divergence.

**Account / data state used:** I did **not** wipe or reseed. The base seed (`seed.ts`) was already applied to org `coheron-demo` ("CoheronConnect HQ"): 18 users, 1 org, 9 employees, full config (chart of accounts, ticket categories, pipeline stages, catalog), and **zero transactional records**. Per `seed.ts`'s own design ("does NOT create bulk demo records"), this recordless-but-configured state **is** the day-one state for every record-driven module, so I observed day-one without a destructive wipe. I did not run the bulk importer this stage (no employee-dependent control was exercised that required more than the 9 seeded). The removed demo-company seed was not reintroduced.

**Runtime observations during bring-up, not predicted by static:**
- Before migrating, the API's `audit-verify` BullMQ loop logged `Job … failed: relation "audit_chain_anchors" does not exist` **on every run** — an automation loop failing continuously because of the missing table.
- On every API boot the server **auto-reseeds/reconciles the chart of accounts** (`[seed-reconcile] chart_of_accounts: org=coheron-demo inserted 28`) — config self-heals at startup.

**The app does run locally** (after migrating). It is not a "will-not-run" dead end — but it took a migration step, and the pre-migration failure mode is a finding in its own right.

## 4 · Everything observed that run-131837 did not predict

1. **🚩 Blocking setup divergence (§1):** local DB was 14 migrations behind head; login returned a raw 500 (`esi_establishment_number` missing); required `db:migrate`. The stack served traffic against an unqueryable schema instead of refusing to start.
2. **🚩 `audit_chain_anchors` missing pre-migration → the `audit-verify` automation loop failed on every execution.** A background integrity loop silently broken by a schema gap. (Resolved by the migrate.)
3. **API auto-reseeds the chart of accounts on every boot** (`seed-reconcile … inserted 28`). Config self-heals at startup — not documented in the static map.
4. **`/app/esg` shows fabricated numbers on a brand-new empty org.** Concrete values rendered with zero backing data: **ESG Score 64, Environmental 62, Social 74, Governance 55, "Scope 1+2 GHG 420 tCO₂e ↓8% vs last year", "Female employees 34% (target 40%)", "Data breaches 0 — 12 months clean"**, plus "SEBI BRSR alignment enabled / GRI mapping active". run-131837 predicted "placeholder"; runtime shows the concrete, and that it is presented as real reporting on an org that has no ESG data — the same class as the ESI-zero shape the brief cited.
5. **`/app/tickets/new` "Assigned To" dropdown is populated with hardcoded person names** (Alex Rivera / Jordan Chen / Sam Okafor / Taylor Patel) that are not the seeded users — and the whole assignment block is discarded on submit (§3, List A).
6. **`/app/finance/accounting/coa` category filters render mis-pluralised labels** — "liabilitys", "equitys", "incomes" (naive `+s`). Cosmetic.
7. **429 rate-limit burst** appeared in the console during rapid automated navigation. **Likely harness-induced** (many tRPC batches fired back-to-back faster than a human), not necessarily a product defect — flagged for honesty, not asserted as a bug.

## 5 · What this run CANNOT attest to

- **Local ≠ deployed.** This is a local dev stack. The deployed Vultr stack differs (per run-131837, its compose ships no object-storage backend, so uploads that "worked or were skipped" here may behave differently there). Prod applies migrations via the `migrator` service, so the §1 blocker is a local-DB-state artifact and may not exist in prod.
- **Coverage is partial.** List B fully exercised (6/6); List A only 3 of 21 controls exercised (plus one positive-validation check); List C partially. The 18 unexercised List-A items and the INCONCLUSIVE List-C items are **record-dependent** and belong to Stage Two.
- **Negative-test matrix largely unrun.** Only empty-submit (tickets/new) and one silent-discard (tickets/new assignment) were driven. Duplicate-submit, invalid-value (malformed PAN / bad state / negative amount / past date), and navigate-away-mid-action were **not** run on any form this stage.
- **Single role.** Everything was as `admin@coheron.com` (owner). No non-admin/RBAC-restricted perspective, no multi-tenant isolation check.
- **No async/worker flows.** Temporal workflows, BullMQ sweeps (beyond the audit-verify log), email (Mailhog), and object storage (MinIO) were not exercised.
- **One data point created.** I created ticket COHE-0001 through the product UI (to test assignment persistence). No records were deleted; no destructive/irreversible operation was run.

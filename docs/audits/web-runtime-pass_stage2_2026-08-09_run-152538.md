## 1 · The walk (customer's order)

### Step 1 — The wizard, end to end

Walked all 7 steps as admin/owner: Welcome → Company profile → India compliance → Invite team → ITSM SLAs → Finance seed → Done.

- **Step 2 (Company profile):** required Name/Industry/Size/City/State/Website/Support-email. State dropdown includes Karnataka, Kerala, Tamil Nadu, Delhi. **Negative — empty Continue: refused** (stays on step, no advance).
- **Step 3 (India compliance):** GSTIN/PAN/CIN/TAN/EPF/State-code required. **Negative — malformed values** (GSTIN `123`, PAN `NOTAPAN99`, CIN `BAD-CIN`, TAN `BAD-TAN`, state `ZZ`): **refused — but SILENTLY.** Continue did not advance; **no field error, no toast, no console message** told me what was wrong (verified screenshot + console). Valid-format values advanced. → *A customer who fat-fingers a PAN is stuck with zero explanation.*
- **Step 4 (Invite team):** exactly as the static map predicted — "Team invitations are sent from Settings → Users & Roles", an "Open User Management" link and "Skip for now". **No employee-creation mutation.** Confirmed.
- **Steps 5–6:** SLA defaults; finance seed ("Apply & Continue").
- **Step 7 — end state:** **"You're all set! 🎉 Your CoheronConnect workspace is configured. Head to the dashboard…"** with **Go to Dashboard / Settings**.

**The org name persisted** ("CoheronConnect HQ" → "Pilot Manufacturing Pvt Ltd" now shows in the header on every page), so the wizard's writes are real.

### Step 2 — Salary structures (created before employees)

The org already had 9 seeded structures (COH-01…09), **all Basic % = 40% (already below the 50% mark)**. On the "New structure" form:

- **Negative — Basic % = 150:** **refused with a named message — "Number must be less than or equal to 100"** (correct upper-bound guard).
- **Statutory case — Basic % = 30 (below 50%):** **accepted silently and persisted** (saved as a 30% structure). **Traced to cause before recording:** this is **by design, not a defect** — the statutory 50% handling is the **PF wage-base clamp at payroll compute time** (per the PF logic exercised in Step 4 below), not a structure-form floor. The structure form's job is to store the CTC template. So "accepted <50%" here is expected; I am folding it into the compute finding rather than reporting it as a separate defect.

### Step 4 — A payroll run (the crux)

Created a **July 2026** run.

- **On creation it showed "0 employees" / all ₹0 (DRAFT).** I started to trace this to cause and **stopped before writing it down as a bug** — a read-only check showed all 9 employees are `active` and all 9 link to a structure by **both** id and `familyId`, so the linkage is fine. Clicking **Execute** (period-lock) flipped it to **"9 employees"** with full totals. **Conclusion: the "0" is the pre-execute draft state, not a defect.** (This is exactly the kind of artefact the brief said to trace before reporting — it would have been a false finding.)
- Walked the 14-step cycle through **Step 9 (Payslips generated)**. Aggregate output:
  - Gross **₹82,52,499** · Total deductions ₹38,08,282 · Net **₹44,44,217** · Employer cost ₹82,70,138
  - **Emp PF ₹15,650 · Empr PF ₹16,962 · ESI ₹833 · Prof. tax ₹1,800 · TDS ₹37,90,676**
- **Every warning the run produced, in full — `Errors (2)`, both naming employee `1c9dfc41-440d-43ca-8f2e-1569e6677432`:**
  > *"Employee is an ESI member this period, but the ORGANISATION has no ESI establishment number — a mandatory payslip field would print blank. Set it in the India setup wizard (org-level fix)."*
  > *"Employee is an ESI member this period, but has no ESI IP number on their record — a mandatory payslip field would print blank. Set the employee's ESI IP number (employee-record fix)."*
  - **Cause:** in the wizard I left **ESI Establishment No. blank** (it is optional), and the employee record has no ESI IP number. Only **one** employee is flagged an ESI member — COH-05 at ~₹20,833/mo, i.e. under the ₹21,000 ESI ceiling; the other eight (₹10L–₹6Cr CTC) are correctly not ESI members. **This is the C6 payslip-identity work firing correctly** — the inverse of the old "ESI hardcoded to ₹0" defect: it computes ESI *and* refuses to let mandatory identity fields go blank silently.
  - **But — the errors did NOT block the run.** The cycle advanced to "Payslips generated" with both errors outstanding, so **payslips were generated for the ESI member with those mandatory identity fields blank.** The errors are advisory, not gating (see §3).

## 2 · What a customer is NOT told that they need to know

1. **The wizard declares "You're all set! 🎉 Your workspace is configured" on an org that has zero employees and cannot run a single payroll.** Nothing at the end of setup, on the Command Center, or anywhere else indicates the workforce is empty and unpayable, or points the customer to add employees + salary structures before payroll is possible. A pilot customer finishing the wizard on 25 August reasonably believes they are done.
2. **Malformed statutory IDs in the wizard are refused with no message.** A bad GSTIN/PAN/CIN/TAN silently prevents advancing — no "invalid PAN format" text, no toast. The customer sees a dead Continue button and no reason.
3. **An admin cannot view an individual employee's payslip from the payroll run.** The run exposes only aggregates and errors; per-employee payslips live behind the employee portal / a PDF-by-id URL. Whoever runs payroll cannot eyeball what a given employee's payslip will show.

## 3 · Accepted that should (arguably) have been refused

This stage found **less** of this shape than Stage One — the statutory path mostly behaved. The two candidates, both traced to cause:

1. **Salary-structure Basic % below 50% is accepted silently.** → **Not a defect.** By design the 50% floor is the PF wage-base clamp at compute time, not a structure-form rule. Folded here, not reported as a bug.
2. **The payroll run generated payslips while two `Errors` about blank mandatory ESI identity fields were unresolved.** The errors are surfaced and clearly worded (good), but they are **advisory, not blocking** — the cycle proceeded to "Payslips generated", so a payslip with a legally-mandatory field (ESI establishment no. / IP no.) blank was produced anyway. Whether a mandatory-field error *should* halt payslip generation is a product decision; recorded as observed. This is an **operational/gating** question, not a computation defect — the amounts are right; the gate is soft.

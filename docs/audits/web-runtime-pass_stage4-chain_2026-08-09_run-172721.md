1. **The chain is segregation-of-duties by design (confirmed).** `payroll.runs.approve` (`apps/api/src/routers/payroll.ts:587–616`) enforces, per step: **HR → `hr.write`**, **FINANCE → `financial.write`**, **CFO → `financial.write`**; plus SoD **by user identity** — you cannot approve FINANCE if you approved HR, nor CFO if you approved HR or Finance. ## 1 · The per-step permission model (traced from code + live)

`payroll.ts:587`: `requiredModule = step === "HR" ? "hr" : "financial"`, checked for `"write"`. So:

| Step | Permission required | SoD constraint | Seed roles that hold it |
|---|---|---|---|
| HR approve | `hr.write` | — | owner (admin), `hr_manager` (hr@) |
| FINANCE approve | `financial.write` | ≠ HR approver | owner (admin), `finance_manager` (finance@) |
| CFO approve | `financial.write` | ≠ HR and ≠ Finance approver | owner (admin), `finance_manager` (finance@) |

(There is a `DISABLE_PAYROLL_SOD=true` env escape hatch in the code — off here.)

## 3 · The RBAC inconsistency (new finding, traced — not a "gap", not "by design")

The **action** permission and the **page-gate** permission are misaligned for this workflow:

- The FINANCE/CFO approval **action** requires **`financial.write`** (held by `finance_manager`).
- The only UI that triggers it — the **payroll run page** — is gated on **`payroll.read`** (held by `hr_manager` and owner, **not** `finance_manager`).
- The payroll approval is **not** mirrored into the Approval Queue that `finance_manager` can see.

Net effect across the seed role model:

| Role | payroll.read (see the page) | financial.write (approve FIN/CFO) | Can complete a FIN/CFO step in the UI? |
|---|---|---|---|
| owner (admin) | ✓ | ✓ | Yes — but SoD limits to **one** step |
| hr_manager (hr@) | ✓ | ✗ | No (403 on approve) |
| finance_manager (finance@) | ✗ (Access Restricted) | ✓ | No (can't open the page) |

**Only the owner holds both permissions, and SoD forbids the owner from doing more than one of the three steps.** Therefore **no combination of the seed roles can complete HR→Finance→CFO through the UI.** This is why the chain stalls — not because SoD is working (it is), but because the role that SoD *requires* for the Finance/CFO steps is locked out of the screen that hosts the button.

**This is the actual defect, and it is an RBAC-configuration inconsistency**, precisely the class you flagged: the payroll page-gate module (`payroll`) and the approval action module (`financial`) disagree. Fixes are configuration-level, not feature work: **grant `payroll.read` to `finance_manager`** (and whatever role plays CFO), **or** surface payroll approvals in the cross-module Approval Queue so `financial.write` holders can act there.

## 4 · How to actually complete the chain (for the next pass)

With the roles as-is, the only route is a **fresh run** where the steps are done by three distinct identities that each hold *both* the page-gate and the action permission — which only the owner does. So completion needs one of:
- **Config fix:** add `payroll.read` to `finance_manager` (and the CFO role), then: HR = hr@, FINANCE = finance@, CFO = a second `financial.write` holder (distinct) — three distinct identities, each able to see the page and approve their step.
- Or provision a third `financial.write` + `payroll.read` identity and start the run with **HR done by hr@** (freeing the owner to be CFO).

Either way it is an RBAC setup, exactly as you said — but the setup is currently **incomplete/inconsistent**, not merely unconfigured.

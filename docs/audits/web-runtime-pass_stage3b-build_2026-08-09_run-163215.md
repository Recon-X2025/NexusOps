## 2 · Accepted that should have been refused

### 🚩 DUPLICATE PAN — ACCEPTED (the headline)

I created **Ravi Kumar with the same PAN as Meera Menon** (`FGHIJ5678K`). It was **accepted with no refusal, no warning** — both employees persist with the same PAN. Two distinct people now share one PAN in the workforce.

**Traced to cause:** PAN is stored with **non-deterministic envelope encryption** (`v2:` prefix, per-row IV → the same plaintext PAN yields *different* ciphertext for Meera and Ravi, visible in the stored values). Consequently:
- a DB unique index on the encrypted column **cannot** catch a duplicate (the ciphertexts differ), and
- the create path does **no plaintext pre-check** for an existing PAN.

So a duplicate PAN passes silently at entry. As the brief anticipated, this is invisible until it **breaks TDS reconciliation at the return** (Form 24Q / 26AS), not at data entry — the worst place to discover it. This is a real defect, not a harness artefact, and it is unaffected by the rate-limit setting.

## 2 · Meera — the >50% wage-base case (captured intermediates)

Meera's salary structure is Basic-heavy (basic = 60% of gross). Payslip captured live:

| Field | Value |
|---|---|
| Gross earnings | ₹1,66,667 |
| Basic | ₹1,00,000 (60% of gross) |
| PF wage base (resolved) | see derivation below |
| Employee PF | **₹1,800** (ceiling-dominated) |
| Employer PF | ₹1,951 (≈13% of ₹15,000 — includes EDLI/admin) |
| ESI | ₹0 (not an ESI member; gross ≫ ₹21,000 ceiling) |
| Professional Tax | ₹0 — **Kerala, flagged** (half-yearly; not computed, see §3) |
| TDS | ₹0 |
| Net pay | ₹1,64,867 |

**Wage-base derivation (traced):**
1. Total remuneration ₹1,66,667 → **50% = ₹83,333**.
2. Basic ₹1,00,000 **> ₹83,333**, so the **50% clamp fires and pulls the base DOWN to ₹83,333**
   (this is the downward clamp shipped in `62b0349`, working as intended).
3. `min(₹83,333, ₹15,000 ceiling) = ₹15,000` → the **statutory ceiling dominates** the clamped base.
4. Employee PF = 12% × ₹15,000 = **₹1,800**.

**Nuance recorded honestly:** Meera *runs* the clamp-down branch (basic > half) but her final PF is
decided by the ₹15,000 ceiling, not by the clamp. A clean *monetary* witness to the clamp would need
`half-of-total < ₹15,000` **and** `basic > half-of-total` (roughly total < ₹30,000, basic-heavy) — no
such employee is in this workforce. **EPS / EDLI / admin are not stored per-payslip** (confirmed: no
such columns on the payslip; the ECR/challan layer recomputes them — §5).

## 5 · The statutory-output layer — traced to cause

### 5.1 Step 13 (`generateStatutory`) is a pure status flip

`apps/api/src/routers/payroll.ts:682` — read in full. It:
- requires `pipelineStatus === "CFO_APPROVED"` (else `BAD_REQUEST`),
- sets `pipelineStatus = "STATUTORY_GENERATED"` + the legacy status,
- returns the mapped row.

**No file, document, challan, or submission record is created.** The run's "Statutory outputs" step
does not produce statutory outputs.

### 5.2 The real generators live elsewhere and are unreachable from the run

The ECR/ESI/PT builders are in `apps/api/src/routers/india-compliance.ts` under `filing.*`
(`filing.submit` at ~line 668, ESI at ~771, PT at ~869). Each:
- takes a **`...SubmissionId` / `...ChallanId`** and reads a **pre-existing** row
  (`epfoEcrSubmissions` / `esiChallanRecords` / `ptChallanRecords`); returns `NOT_FOUND` if absent;
- rebuilds the payload from the payroll run behind that record and enqueues a portal-push workflow.

**Reachability (decisive):** a repo-wide search for `insert(epfoEcrSubmissions|esiChallanRecords|ptChallanRecords|tdsChallanRecords)`
across `apps` + `packages` returns **only test files** (`esi-return.test.ts`, `pt-challan.test.ts`,
`statutory-filing.test.ts`). **No production/runtime path creates any of these records.** The
`filing.*` procedures only ever `.select()` or read-by-id. So in a real org there are zero submissions
to file, `filing.submit` returns `NOT_FOUND`, and the run's step 13 does not create them either. **The
compute→file loop is open at both ends.**

### 5.3 What the ECR builder *would* emit (read from code; defects noted)

From `india-compliance.ts:710-733` + `lib/india/ecr-format.ts:32-48`:

- **Delimiter `#~#`;** header row present: `#~#${orgEpfoId}#~#MM/YYYY#~#ECR`.
- **Establishment id is a synthesized placeholder:** `orgEpfoId = "EPFO_" + org.id.slice(0,8).toUpperCase()`
  — the org UUID prefix, **not a real EPFO establishment code**.
- **11 body fields:** `uan, memberName, grossWages, epfWages, epsWages, edliWages, employeeEpf,
  employerEps, employerEpf, ncp, refund`.
- **`epfWages = min(Number(slip.basic), 15000)`** — derived from the payslip's **raw `basic`**, ceiling-capped —
  **not** the resolved (>50%-clamped) wage base. But **`employeeEpf = Number(slip.pfEmployee)`** — the
  contribution the cycle computed on the **resolved/clamped** base. **These disagree whenever the 50%
  clamp bites and basic < ₹15,000** (contribution ≠ 12% of reported wages → EPFO portal reject/flag).
  For Meera specifically they happen to agree (basic ₹1,00,000 > ceiling → both collapse to ₹15,000 /
  ₹1,800), so **Meera does not witness this bug**; a mid-band basic would.
- **`memberName = emp.employeeId`** — the internal employee **code** (e.g. `COH-0007`), **not the
  person's name** that EPFO expects.
- **`ncp = 0` hardcoded** for every member — loss-of-pay days are never reflected in the ECR.
- `epsWages = edliWages = min(basic,15000)`; `employerEps = min(round(pfWages*0.0833),1250)`;
  `employerEpf = Number(slip.pfEmployer)`; `refund = 0`; `uan` falls back to `"UNKNOWN"`.

### 5.4 ESI challan (read from code)

`india-compliance.ts:812-834` maps **every** payslip: `employee = round(gross*0.0075)`,
`employer = round(gross*0.0325)` — **recomputed on gross, with no ≤₹21,000 membership filter** (a code
comment rationalises this as "let the portal reconcile against the ceiling"). Consequence: **Meera
(payslip ESI ₹0, not a member) would appear in the ESI challan with ~₹1,250 / ~₹5,417** — the challan
contradicts her own payslip. Same defect shape as the ECR: recompute-from-gross diverges from the
payslip's membership-aware stored value.

### 5.5 PT challan (read from code)

`india-compliance.ts:906-918` filters `slips.filter(s => Number(s.professionalTax) > 0)` and uses the
stored `professionalTax`. So the Kerala/Tamil-Nadu **flagged-not-computed** employees (PT = ₹0) produce
**no PT line at all** — consistent, but the half-yearly states emit nothing.

### 5.6 A separate, real per-employee output does exist (not exercised)

`payroll.runs.generateForm16ToDms` (`payroll.ts:1001`, `payroll.write`) decrypts the stored (envelope)
PAN and writes a **Form-16 PDF to DMS** — a genuine artefact. It is **not** invoked by step 13, is
per-employee/on-demand, and needs the DMS/S3 backend the deployed stack currently lacks (see the
document-storage sweep in `docs/CONTEXT.md`). Not driven this stage.

## 6 · Duplicate-PAN behaviour (Meera + Ravi share a PAN)

**PAN does not appear in any of the ECR / ESI / PT outputs** — those key on UAN and `employeeId`. So a
duplicate PAN is **invisible** to these returns: it neither de-duplicates nor collides; both employees
emit independent lines under their own UAN/employee code. PAN only surfaces in the TDS/Form-16 path
(§5.6), which was not exercised. **A duplicate PAN is therefore silently carried into statutory
filings with no detection at the return-generation layer.**

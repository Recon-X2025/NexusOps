## 0 · Headline

- **The signal works and updates live**, and its copy names what is missing and where to go.
  Empty org → "No employees… / No salary structures…"; after a structure → only the employee
  blocker; after a complete employee → panel disappears, `ready: true`.
- **The wizard's final step now reads "Setup complete!"** and points at the dashboard's
  "Before you can run payroll" panel. On the Command Center that panel renders **above the fold**,
  directly under the four getting-started items.
- **THE FINDING — "ready" does not mean "can run *this* month."** A structure created on the setup
  day is effective **from that day**. The readiness signal (correctly, per its stated scope) checks
  only that a structure is *assigned* — not that its effective-date window covers the period being
  run. So an org told **"ready"** locked an **August** run showing real money (₹65,000, 1 employee),
  then **payslip generation silently produced 0 payslips and ₹0** — `workflow_metadata.errors = []`,
  no message naming the employee or the cause. This is simultaneously a *ready-but-can't-run* case
  and the *refuses-without-a-message* pattern. A September run (structure effective) paid all three.
- **PT (owner's mid-walk ask) computes correctly per state:** Maharashtra ₹200, West Bengal ₹200,
  Kerala ₹0 **flagged** (half-yearly, six-month income unavailable). The Kerala flag names the
  employee by **raw user UUID**, not name/code — a UX wart.

## 7 · Does "ready" mean "can run"? — the finding (Item: the finding condition)

I drove a real payroll run to test it.

- **August 2026 run** (the default a 25-Aug pilot gets): **locked** showing **"1 employees · Net ₹63,200",
  Gross ₹65,000, Emp PF ₹1,800, Empr PF ₹1,951** — so at lock, "ready" looked true. But at **Step 9
  Payslips generated the run collapsed to "0 employees · ₹0"** across every field. DB confirms
  `pipeline_status=PAYSLIPS_GENERATED`, `workflow_metadata.errors=[]`, **0 payslip rows**.
- **Cause (traced):** the structure's `effectiveFrom` is the day it was created (2026-08-09), which
  postdates the August period start (Aug 1). `lockPeriod`/totals join the structure directly (no
  effective-date test) and count the employee; `computePayslips` resolves the version *in force for the
  period* (`resolveSalaryStructureForPeriod`), finds none covering Aug 1, and **silently `continue`s** —
  no skip recorded. So the org told "ready" produced **zero payslips for August, with no message**.
- **September 2026 run** (structure effective for Sep 1): all **3 employees** paid — Gross ₹1,95,000,
  Net ₹1,89,200, 3 payslip rows. So the org *can* run payroll, just not for a month before the structure's
  effective date.

**This is a real limitation.** It is *not* a defect in the readiness signal's stated conditions (structure +
employee + state are all genuinely present). But it means **"ready" over-promises**: it does not verify the
structure's effective-date window covers the period the customer will actually run, and the payroll cycle
then drops the employee **silently** at payslip generation. For a 25-Aug pilot running August, that is
exactly the "told ready, gets nothing, with no explanation" trap.

## 8 · PT computation (owner's mid-walk request)

Added a Maharashtra employee (Ravi, EMP-0002) and a West Bengal employee (Sourav, EMP-0003), both on the
same structure, and ran **September** (so payslips generate). Per-employee, read from the DB (gross ₹65,000 each):

| Employee | State | PT | Basis |
|---|---|---|---|
| EMP-0001 Anil | Kerala | **₹0** | Half-yearly — **flagged**, not computed |
| EMP-0002 Ravi | Maharashtra | **₹200** | Monthly slab (> ₹10,000 → ₹200; ₹300 only in February) |
| EMP-0003 Sourav | West Bengal | **₹200** | Monthly slab (> ₹40,000 → ₹200) |

Aggregate **₹400** — matches the run summary. Monthly-PT states compute the flat slab; the half-yearly state
(Kerala) is **not guessed** — it is flagged:

> "Half-yearly professional tax for "Kerala" could not be computed this collection month because the full
> six-month income is not available: earlier payroll is missing (April, May, June, July, August) — a
> data/migration gap. No PT was deducted. Supply the missing months' payroll and/or record this period's PT
> manually before locking."

Correct behaviour. **Wart:** the flag identifies the employee by **raw user UUID**
(`14b22d48-4bd2-45fe-a6fc-b2d5516c67b7`), not "Anil Kumar" / "EMP-0001" — a customer can't tell who it means.

## 10 · Judgement — would a first-time customer know what to do?

**For the standing "can't run payroll yet" state: yes.** The panel is in plain language, above the fold,
names the two things missing, and links to the exact tabs where each is created — both destinations check
out. The wizard's final line now points here instead of claiming "You're all set." A person who has never
seen the product would read "No salary structures — Payroll → Salary structures" and know the next move.

**But there is a real gap the customer would hit next:** having done both, they are told **"ready"**, run
their first (August) payroll, and get **zero payslips with no explanation** — because their brand-new
structure isn't effective until the day they created it. Nothing tells them to set the structure's effective
date to the start of the period, and the run swallows the drop silently. So the signal communicates the
*first* step well and then hands the customer to a cliff it doesn't warn about. **Plainly: the readiness
message communicates; the transition from "ready" to a real August payslip does not.**

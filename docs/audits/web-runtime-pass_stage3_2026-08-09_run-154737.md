## 3 · The 429 rate-limit storm (blocked the build; cause unresolved)

The first valid create silently failed. The console was **flooded with `429 Too Many Requests`**, and the create mutation was among the rejected requests (DB confirmed no employee created). Traced into the API:

- The limiter (`apps/api/src/index.ts:276+`) keys **per session-token + per-endpoint** (`user:<token>:<endpoint>`), dev per-token max ~10k/min, plus a burst limiter (~33k/5s), buckets in Redis with a ~60s TTL.
- The web client uses tRPC **batching** + react-query **retries**: once the sidebar's `dashboard.getMetrics` poll trips a bucket, failed batches retry in a tight loop and sustain the 429s.

**Cause is genuinely unresolved** between (a) a limiter/retry interaction that a real tenant could hit, and (b) **my automated driving** — hundreds of tool-driven page loads, each firing many tRPC queries, plausibly exhausting a dev bucket in a way no human would. I lean toward (b) as the trigger of the *volume*, but cannot rule out (a).

**What is a real finding regardless of cause:** when the create was rejected by 429, **the form stayed open and showed the user nothing** — no toast, no inline error. The mutation failed silently; only the browser console revealed it. Any 429 (whatever its origin) surfaces to the user as a dead button. This is the same "refused without telling you why" shape as Stage Two's wizard.

A second create attempt ~a minute later produced **no 429** (buckets had aged out) but still didn't persist — by then the modal had re-rendered and lost its name/email state, so the block was almost certainly empty-required-fields, not the limiter. That is form-interaction fragility under automation, not necessarily a product defect; I note it as a reason I stopped, not as a finding against the product.
